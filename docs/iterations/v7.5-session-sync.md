# Version 7.5 — Session sync and physio report

Status: planned
Source: §13–14

Built on Supabase, not Firebase — see v7.3-supabase-auth.md for why.

Scope: WorkManager backoff, immutable version binding, minimal report and chart.

## Schema

Continuing v7.4's relational translation of §13.1/§13.2:

```sql
create table public.sessions (
  id uuid primary key default gen_random_uuid(),
  assignment_id uuid not null references public.assignments(id),
  patient_id uuid not null references public.users(id),
  started_at timestamptz not null,
  ended_at timestamptz,
  set_score double precision,
  completion_rate double precision,
  degradation_onset_rep int,      -- §6.18's CUSUM change point, null when fatigue never fired
  device_fps double precision,
  delegate text                   -- NPU/GPU/CPU, logged per §12.2
);

create table public.reps (
  session_id uuid not null references public.sessions(id),
  index int not null,
  quality double precision,
  rom double precision,
  duration_ms int not null,
  valid boolean not null,
  partial boolean not null,
  jerk double precision,
  primary key (session_id, index)
);

create table public.fault_events (
  id uuid primary key default gen_random_uuid(),
  session_id uuid not null references public.sessions(id),
  rep_index int not null,
  fault_id text not null,
  z_at_fire double precision not null,
  t_fire_ms int not null
);

create table public.cue_events (
  id uuid primary key default gen_random_uuid(),
  fault_event_id uuid not null references public.fault_events(id),
  cue_variant text not null,
  z_at_fire double precision not null,
  z_at_2s double precision,
  z_next_rep double precision,
  resolved boolean not null default false
);

create table public.feature_samples (
  session_id uuid not null references public.sessions(id),
  rep_index int not null,
  feature text not null,
  z double precision,
  primary key (session_id, rep_index, feature)
);

create table public.prescribed_reps (
  session_id uuid not null references public.sessions(id),
  prescribed_reps int not null,
  primary key (session_id, prescribed_reps)
);

create table public.rejection (
  rep_id uuid not null references public.reps(id),
  rejection double precision,
  primary key (rep_id)
);

create table public.smoothness_sparc (
  rep_id uuid not null references public.reps(id),
  smoothness_sparc double precision,
  primary key (rep_id)
);
```

`sessions.assignment_id` carries `exercise_id`/`exercise_version` by way of `assignments`
(§13.4: the patient's session is bound to the assignment's exercise version, and a physio edit
during a live set creates a new version rather than mutating the one already bound).

## Sync mechanics — unchanged from §13.3–13.4

- **Room stays authoritative.** A `Rep` row is written as each rep completes, not at set end, so a
  killed session is still partially recoverable. This is a property of the local write path and does
  not depend on which cloud vendor eventually receives the mirror.
- **WorkManager with exponential backoff** pushes queued sessions/reps/faults/cues from Room to the
  tables above. Retries use `upsert` on the primary keys shown, so a duplicate retry is a no-op
  rather than a duplicate row — the idempotency the plan asks for, achieved by key shape rather than
  a separate dedup pass.
- **Last-write-wins**, same as the plan specifies for Firestore. `.rpose` immutability (§9.6) means
  the one conflict worth naming — a physio editing an exercise mid-session — cannot corrupt anything:
  the session is bound to a specific `(exercise_id, exercise_version)` pair that the edit does not
  touch.

## RLS

Same shape as v7.4: sessions/reps/fault_events/cue_events readable by the owning patient and by the
physio who owns the exercise the session's assignment points at. Write this out per table before the
device gate.

## Outstanding — the pausing risk

A Supabase free project auto-pauses after 7 days with no database activity (data frozen, not lost,
restorable from the dashboard for up to a year). For a hackathon this is workable but not free of
attention: rehearse the demo, then either run one query a week until presentation day, or restore
the project the morning of and confirm sync still works before going on stage. Not a blocker to
building this iteration — a note for whoever owns demo-day logistics.

## Result

_(filled in after the iteration lands)_

Filled in 2026-09-05. Implemented as specified, with the schema extended beyond the sketch above:
`feature_samples` (per-rep per-feature z aggregates, keyed `(session_id, rep_index, feature)`) and
`prescribed_reps` on `sessions` were added so the report can show counted against prescribed, and
`rejection`/`smoothness_sparc` on `reps` follow v7.1's naming (SPARC is not jerk). Unfinished
sessions upload only once 30 minutes stale, so a patient resting between sets is not pushed
mid-rest. The worker is logic-free: `syncWorkResultFor` maps Done/Offline/Failed to
success/retry/failure as a plain function. 16 tests in `SessionSyncTest` against real Room under
Robolectric; suite is 614, all passing. Outstanding: the two-device gate, and one more
`schema.sql` run against the live project.
