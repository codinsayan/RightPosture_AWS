# Version 7.4 — Invite and assignment sync

Status: in-progress
Source: §0, §13

Built on Supabase (Postgres + Storage), not Firebase — see v7.3-supabase-auth.md for why.

Scope: six-character invite, one-time link, exercise metadata and assignment sync.

Tests: valid, invalid, reused/expired, collision, and retry cases against the schema below.

Device gate: physio code links patient and assignment appears.

## Schema

§13.1's Room entities stay exactly as specified — they are local and vendor-independent. What
changes is §13.2's **Firestore mirror**, which becomes Postgres tables instead of a document tree.
Same information, relational shape:

```sql
create table public.users (
  id uuid primary key references auth.users(id),
  role text not null check (role in ('physio', 'patient')),
  name text not null,
  email text not null
);

create table public.exercises (
  id text not null,
  version int not null,
  physio_id uuid not null references public.users(id),
  name text not null,
  rpose_path text not null,      -- Storage object path, not the bundle itself
  demo_path text,                -- Storage object path for demo.mp4, nullable per §9 (optional)
  created_at timestamptz not null default now(),
  primary key (id, version)      -- §9.6 immutability: an edit is a new row, not an update
);

create table public.invites (
  code text primary key,          -- six characters, §0
  physio_id uuid not null references public.users(id),
  created_at timestamptz not null default now(),
  expires_at timestamptz not null,
  used_by uuid references public.users(id),
  used_at timestamptz
);

create table public.assignments (
  id uuid primary key default gen_random_uuid(),
  exercise_id text not null,
  exercise_version int not null,
  patient_id uuid not null references public.users(id),
  reps int not null,
  sets int not null,
  rest_seconds int not null,
  sequence_index int not null,
  active_from timestamptz not null default now(),
  active_to timestamptz,
  foreign key (exercise_id, exercise_version) references public.exercises(id, version)
);
```

`invites.code` as the primary key makes reuse and collision the same check: an `insert` that
violates the key is a collision, a lookup that finds `used_by is not null` is a reuse, a lookup
past `expires_at` is expired. Three of §13.4's "final schema" edge cases fall out of two column
constraints rather than needing application logic.

## Row Level Security

Supabase's equivalent of Firestore's security rules, and mandatory before any device gate — without
it every authenticated user reads every row. Sketch, refined once 7.3's role claim exists:

```sql
alter table public.assignments enable row level security;
create policy "patients see their own assignments"
  on public.assignments for select
  using (patient_id = auth.uid());
create policy "physios see assignments they created"
  on public.assignments for select
  using (exists (
    select 1 from public.exercises e
    where e.id = exercise_id and e.version = exercise_version and e.physio_id = auth.uid()
  ));
```

One policy per table per operation, not one blanket rule — write these out in full before the device
gate, do not ship with RLS disabled "temporarily."

## Result

The schema sketched above is what shipped, with two corrections found by reading it against the
device gate rather than against the plan.

**A physio could not see their own patients.** Every `select` policy on `public.users` restricted a
caller to their own row, so after a patient redeemed a code there was nobody for the physio to
assign to - the second half of the gate was unreachable. `is_linked_patient(uuid)` plus a matching
policy fixes it. The redeemed invite is the link; no join table was needed. The mirror was wrong the
same way: `is_linked_physio` was defined through `assignments`, so a patient who had linked but not
yet been prescribed anything could not read their physio's name, which is exactly the window between
the two halves of the gate.

**Redemption became a function, not a policy.** The RLS sketch above gave patients `select` and
`update` on any open invite. That is a read followed by a write, so two patients on the same code
could both see it as open and the second would overwrite the first; it lets any signed-in user page
through every live code; and it cannot distinguish expired from used from unknown, because a policy
tight enough to be safe returns an empty set for all three. `redeem_invite(text)` is
`SECURITY DEFINER`, takes a row lock with `select ... for update`, and returns one of `ok`, `used`,
`expired`, `unknown` or `unauthenticated`. Patients now have no read access to `invites` at all.

Redeeming your own code twice returns `ok`. A patient who reinstalls has to end up linked, not
locked out.

### Retry

Status 0, 5xx and 429 are retried with doubling backoff. 4xx is not - resending identical bytes
earns an identical rejection. 409 is called out explicitly: an invite collision needs a *different*
code, so it is handled by regenerating in `InviteRepository.create` rather than by the generic
helper.

### Ordering

The `.rpose` is uploaded before its row is registered. The other order fails unrecoverably: a row
with no upload behind it is an exercise the patient can see and cannot start, and the retry would
re-register the row rather than supply the missing bytes. Downloads land in a `.part` file and are
renamed once whole. Assignment ids are generated on the device, so a request that timed out after
the server committed it replays as the same row rather than a second prescription.

### Still open

`supabase/schema.sql` has to be re-run before any of this works - verified against the live project
that `redeem_invite` returns `PGRST202` until then. The device gate needs two accounts and has not
been run. Prescriptions are fixed at 3 x 10 with 60 s rest; letting the physio choose is a form, and
it can wait until the path it feeds is proven.
