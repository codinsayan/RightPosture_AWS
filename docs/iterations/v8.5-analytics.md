# Version 8.5 — Analytics: trend and per-rep charts

Status: complete  
Source: §14.1, §14.2, §6.18.5, §6.21, §6.6

Scope: an analytics screen shared by both roles, a within-session quality curve with the change
point marked, an across-session trend curve, and joint attribution with the magnitude it currently
discards.

Tests: an unscored rep is a gap and never a zero; series are plotted against `repIndex`; a session
that cannot be judged breaks the trend rather than dropping to zero; charts never interpolate across
a gap.

Gate: no chart states a measurement that was not taken, and no absent value is drawn as zero.

---

## Why

§14.1 promises the physio "per-set quality curve, degradation change-point marked, attribution", and
§14.2 promises the patient "quality-per-rep chart with the change point marked" plus "progression
curves toward goal, per metric". Neither exists — the session report is a flat list of `Text` rows.
`AppHost.kt:606-612` says so in a code comment, and `v7.2-role-navigation.md:100` lists it as
outstanding.

The data has been on disk since 7.1. Nothing reads it.

## No schema change

Every column this needs already exists.

| Need | Column |
|---|---|
| quality curve | `reps.quality` (nullable — the gap), `reps.repIndex` (the x axis) |
| change point | `sessions.degradationOnsetRep` |
| trend | `sessions.startedAt`, `sessions.exerciseId` |
| joint attribution | `feature_samples.meanSignedZ`, `.frames` |

`RightPostureDatabase.kt` must show a **zero diff**. `fallbackToDestructiveMigration(dropAllTables =
true)` is armed at line 53, so a `version` bump without a matching migration silently destroys every
session recorded on the device. Adding `@Query` methods to a DAO is schema-neutral.

## Abstention is the whole design (§6.6)

Three rules, and they are the reason this is an iteration rather than an afternoon:

1. **An unscored rep is a gap, not a zero.** `reps.quality` is null when no frame could be scored.
   Plotting that as 0 claims the patient performed terribly; the truth is nobody measured.
2. **Plot against `repIndex`, not list position.** `repIndex` is 1-based and counts *every* finished
   rep including rejected ones, so a valid-only series has genuine holes in x. Using list position
   slides rep 4 into rep 3's slot and quietly relabels the data.
3. **A session that cannot be judged breaks the curve.** `SessionMetrics.countsTowardProgression` is
   false below 6 valid reps (§6.21.1). Such a session is excluded from the median — it must not be
   drawn at zero, and the curve must not interpolate straight through it either.

`Progress.NoData` and `Progress.GoalNotSet` must look different from `Progress.Known(0.0)`. §6.21.3
is explicit: a screen showing "100% progress" because no goal was set is a lie the patient acts on.

## Shape

**`data/Daos.kt`** — two queries. `sessionsForExercise(exerciseId)` ordered `ASC` (§6.21.2's window is
the *last* three and §6.21.6 counts *consecutive* sessions, so arrival order changes the verdict), and
`repsForSessions(ids)`. The second also fixes the N+1 in `progressionFor` (`AppHost.kt:559-583`), which
issues one `reps(session.id)` per session — 60 round trips for one screen. Aggregation stays in Kotlin:
`medianOf`, `romPeakOf` and the null-vs-zero rule are not expressible in SQLite without lying about
abstention.

**`report/Analytics.kt`** (new, pure) — `ChartPoint(x, y: Float?)` where a null y *is* the abstention;
`segmentsOf` splitting a series into contiguous measured runs; `repQualitySeries`; `sessionTrendSeries`;
`analyticsOf` reusing `sessionMetricsOf` and `evaluateProgression` verbatim, picking the baseline
exactly as `progressionFor` does. `segmentsOf` is the only new abstraction worth having — every chart
draws `segmentsOf(points).forEach { drawPath }`, so one test pins the no-interpolation rule for all of
them at once.

**`report/SessionFacts.kt`** — recover the discarded magnitude. `changesAfterOnset` (line 57) computes
each joint's shift and then throws the magnitude away at line 82, keeping only the sign. Extract
`jointShiftsOf` returning `shiftZ` plus `preFrames`/`postFrames`; `changesAfterOnset` becomes a thin
map over it with the same `MIN_REPORTABLE_SHIFT = 0.5` and `MAX_REPORTED_CHANGES = 2`, so no existing
test moves. Add `MIN_TRUSTED_FRAMES = 5`: `frames` is the trust column, and a 3-frame artefact must not
outrank a 90-frame finding — low-frame shifts are excluded from ranking but still shown, muted, as
"measured on too few frames to judge".

**`nav/Charts.kt`** (new) — copy the `authoring/ReferenceReview.kt:137-159` idiom exactly: `Canvas`
at `fillMaxWidth().height(160.dp)`, `background(Color(0x11000000))`, a `semantics` block, local
`fun x(i)`/`fun y(v)`, `span = (max - min).takeIf { it > 1e-6f } ?: 1f`. File-top `private val` hex
constants; the app does not use theme colours in charts.

- `QualityCurve` — y **fixed 0..100**, not data-derived. A derived span makes a flat 90 look like a
  collapse and makes two sessions non-comparable. `QUALITY_BAR = 80` as a faint rule, change point as
  a vertical `BOUNDARY` line (the same way `TraceChart` draws rep boundaries). Filled dot if counted,
  hollow ring if scored but not counted, **nothing** where quality is null.
- `TrendCurve` — ROM keeps a derived scale, having no natural ceiling. A muted hollow marker at each
  gap, so an excluded session reads as present-but-unjudged rather than missing.
- `JointShiftBars` — width ∝ `abs(shiftZ)`, red drifting away / green drifting back, low-frame rows
  at 40% alpha.

Degenerate cases matter: `x(i) = width * i / (n-1).coerceAtLeast(1)` pins a lone point to the left
edge, so `n == 1` draws one centred dot and `n == 0` composes no Canvas at all — just the house-style
muted empty sentence. No text inside a Canvas: the app has no `TextMeasurer` and adding one breaks
house style.

**`nav/Navigation.kt`** — `data class Analytics(val exerciseId: String?) : Screen`. A data class, not
two screens: `NavState`'s duplicate-push guard and `popTo` both rely on data-class identity, so
`Analytics(null) → Analytics("rp_knee")` is an ordinary push. Mirrors `SessionReport`.

**`nav/AnalyticsScreen.kt`** (new) and buttons on both homes. Follows the reload-on-navigation pattern
at `AppHost.kt:149-154`. **Clear `analytics` to null before loading**: on `Analytics("a") →
Analytics("b")` the effect re-runs with stale state held, and a chart labelled "b" drawn from "a"'s
data is a wrong clinical reading, not a flicker.

## Roles

Both roles see identical content, readiness verdict included, as decided by the project owner.

Recorded because the specs differ: §14.2 grants the patient charts and the summary but not the flag
badges, and §6.21.5 says "notify the physio, never auto-advance — requiring clinician sign-off". A
patient reading "ready to progress" may act on it without their physio. The call was made knowingly;
this note exists so the tradeoff is not rediscovered as a bug.

## Out of scope — cues

§14.1's cue-effectiveness table is not buildable. `BundleAssembly.kt:116` sets `faults =
FaultSet(emptyList())`, so `FaultDetector` never fires, `CueArbiter` selects nothing, and
`fault_events`/`cue_events` are never written in production — the only callers of `upsertFault`/
`upsertCue` are in tests. Persisting `CueArbiter.log` would produce an empty table until 8.1 defines
faults. The existing `cues() → cueTallies → SummaryFacts.cues` seam is left exactly as it is.

## Tests

Pure JVM in `AnalyticsTest.kt`; no Robolectric, because every decision that could be wrong is a pure
function and the composables only scale and draw.

- an unscored rep is a gap, not a zero point
- reps 1, 2, 4 valid produce x = 1, 2, 3, 4 with a null at 3 — not 0, 1, 2
- `segmentsOf` never joins across a gap
- a 4-rep session yields `y == null` rather than a zero
- a single scored session still produces a drawable point
- an exercise with no sessions returns an empty series rather than throwing
- `analyticsOf` orders oldest-first, because the progression window depends on it
- `jointShiftsOf` keeps the magnitude while `changesAfterOnset`'s output is unchanged
- a joint measured on too few frames is not ranked first

`NavigationTest.kt`: analytics is reachable from both roles and `back()` returns to the right home;
`Analytics("a") != Analytics("b")`, mirroring the existing `SessionReport` test.

## Result

Built as planned. 691 tests, up from 675; `RightPostureDatabase.kt` shows a zero diff, so the
destructive-migration guard was never in play.

`report/Analytics.kt` holds the arithmetic — `ChartPoint`, `segmentsOf`, `repQualitySeries`,
`sessionTrendSeries`, `analyticsOf` — and `nav/Charts.kt` the three Canvas composables. `Screen`
gained `Analytics(exerciseId: String?)`, reachable from "Progress over time" on the physio home and
"My progress" on Today.

`jointShiftsOf` now carries the magnitude `changesAfterOnset` used to discard; the prompt-facing
function became a thin map over it, so the chart and the sentence cannot drift apart. `JointShift`
gained `trustworthy` off `MIN_TRUSTED_FRAMES = 5`, sorting untrustworthy rows last but still
rendering them at 40% alpha — a nine-sigma shift seen on three frames is worth showing and worth not
believing.

Two N+1 queries went with it: `progressionFor` was issuing one `reps(session.id)` per session (sixty
round trips to draw one screen) and the session report was doing the same per rep for feature
samples. Both are one query now, via `repsForSessions` and the `allFeatureSamples` that already
existed.

### What the tests are really pinning

Three cases, all the same rule from a different angle, and all of them things a chart gets wrong
silently:

- `repQualitySeries` plots reps 1, 2, 4 at x = 1, 2, 4. By list position it would be 0, 1, 2, sliding
  rep 4 into rep 3's slot and relabelling which rep the drop belonged to.
- `segmentsOf` returns two runs across a gap, and the test asserts the last x of one is not the first
  x of the next — because `points.forEach { lineTo(...) }` is the natural way to write it and draws a
  line straight through the missing rep.
- A four-rep session yields `y == null`, not `0.0`, and keeps its x position. Dropping it compresses
  the axis and hides that the patient turned up; flooring it claims they scored nothing.

### Outstanding

`romGoal` is still null everywhere, so §6.21.3's guard reports "no range goal set" rather than a
readiness percentage. That is the honest rendering and not a bug, but the goal-setting screen is what
turns these curves into progress *toward* something.

The verdict is shown to patients as well as physios, which §14.2 does not grant and §6.21.5 argues
against. Decided by the project owner; the screen carries "Your physiotherapist decides when to move
you on." underneath, which is the least the wording can do.

Charted on device only against synthetic history so far — the phone was unplugged when this landed.
