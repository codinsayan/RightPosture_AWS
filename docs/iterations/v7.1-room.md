# Version 7.1 — Room offline source of truth

Status: in-progress (device gate outstanding)
Source: §13.1, §13.3

Scope: minimum exercise, assignment, session, rep, fault, and cue persistence.

Tests: in-memory DAO and completed-rep recovery.

Device gate: entire patient session works in airplane mode.

---

## The one sentence this iteration is built around

§13.1: *"Persist a `Rep` row **as each rep completes**, not at set end. If the app is killed mid-set,
the session is still partially recoverable."*

Everything below exists to make that true, and the rest of the schema is the minimum needed to give
that row somewhere to live.

## Schema

Seven tables in `data/`, following §13.1 with three departures, each recorded here rather than
discovered later in a diff:

| Departure | Why |
|---|---|
| **No `User` table.** | 7.3 owns identity. 7.1 must work with nobody signed in, so `patientUid` is a nullable column, not a foreign key to a table that has no rows. |
| **`Rep` stores `rejection`, not `partial`.** | §13.1 lists `valid` *and* `partial`. `partial` is derivable from the rejection reason, and two columns that can disagree about the same fact are a bug waiting to happen. Storing the reason keeps strictly more information — §14's report can say *why* a rep did not count. |
| **`Rep.jerk` is named `smoothnessSparc`.** | §6.18.5's smoothness term is spectral arc length, which is not jerk. A physio report labelled "jerk" while showing SPARC would mislead the one person qualified to read it. |

Two keying decisions worth stating:

- **`exercises` is keyed `(id, version)`.** §9.6 makes bundles immutable — an edit is a new row, not
  an update. A session recorded against version 1 can still name what it was scored against after
  the physio publishes version 2, which is what §13.4 relies on to make the interesting conflict
  harmless.
- **`reps` is keyed `(sessionId, repIndex)`**, a natural key rather than a surrogate id. That is what
  makes §7.5's retry idempotent for free: replaying rep 4 of a session hits the same row, so a
  duplicated sync is a no-op instead of a duplicated rep. Every insert is `REPLACE` for the same
  reason.

`sessions.assignmentId` and `sessions.patientUid` are both nullable. The 7.1 flow is exactly: physio
records a reference, then performs a set against it immediately. No assignment exists, and 7.3 has
not happened. A schema that demanded either would fail the airplane-mode gate on its first row.

## Where the write happens, and why there

The rep is persisted from the 33 ms UI sampler in `CameraPreviewScreen`, not from the analysis
thread that produced it.

This is deliberate and it is a trade. §12.2 requires nothing after `onFrame` to be asynchronous, and
disk I/O on the camera thread drops frames — which would corrupt the very measurement being saved.
The cost is a window of at most one sampler tick in which a kill loses the rep that just finished.
Every rep before it is already durable. Losing ~33 ms of the newest rep is a much better failure than
dropping frames on every rep.

The session row is opened *before* the first rep, so a set the patient abandons after zero reps is
still a fact on disk. "Started and did nothing" and "never started" are different clinical
observations and only the first one is evidence.

`finishSession` writes only a summary — set score, completion rate, §6.18.3's change point — over rows
that are already durable. Losing that write costs the summary and nothing else.

## The bundle now exists as a file

`Exercise.rposePath` has to point at something. Until now the bundle lived only in memory, so
accepting a reference writes it to `filesDir/exercises/{id}_v{version}.rpose` and records the path.
A row pointing at nothing would have been a broken row, and 7.4/7.5 need a real file to upload.

## Build changes

Room needed KSP, which needed two things this project did not have:

- `android.disallowKotlinSourceSets=false` in `gradle.properties`. AGP 9's built-in Kotlin support
  rejects the `kotlin.sourceSets` DSL that KSP uses to register generated sources; this is the
  escape hatch AGP's own error message names. Revisit when KSP supports built-in Kotlin natively.
- **Room 2.7.1, not 2.6.1.** 2.6.1 fails under KSP2 with `unexpected jvm signature V`. `SessionDao`
  is also an `abstract class` rather than an `interface`, because the `@Transaction` method needs a
  real body and a suspend default method on an interface is what KSP chokes on.

Robolectric was added for the DAO tests. Pinned to `@Config(sdk = [34])` — it ships android-all jars
per API level and has none for the project's compileSdk 36. The schema does not vary by API level,
so the pin costs nothing.

## Tests

`SessionPersistenceTest`, 10 cases, against a **real in-memory Room database** rather than a fake
DAO. A fake would prove the repository calls the methods it says it calls, which is not the thing
that goes wrong. What goes wrong is the schema — a foreign key that rejects a legitimate insert, a
composite key that does not compose, an upsert that duplicates instead of replacing — and none of
that is visible without SQLite actually running.

- a rep is durable the moment it completes, with no `finishSession` call anywhere in the test;
- a session killed mid-set keeps all five completed reps and comes back from `unfinishedSessions()`;
- a finished session is no longer offered for recovery, and carries its change point;
- re-recording the same rep replaces rather than duplicates (§7.5's idempotency, proven);
- an unscored rep stores `null` quality, not zero (§1.6);
- feature samples land beside their rep and keep the **sign** (§6.18.5 attributes on signed mean);
- clearing takes reps and samples with the session;
- a session records the exercise version it was scored against (§13.4);
- two versions of one exercise coexist (§9.6);
- a session with no assignment and nobody signed in is a valid row.

Command: `./gradlew testDebugUnitTest`.

## Post-review fixes — 2026-09-05

A gap analysis before the device gate turned up one real defect in the wiring above, plus one
untested claim.

**The watermark advanced before the write was confirmed.** The UI sampler set
`persistedReps = record.reps.size` and *then* wrote, catching failures with a log. A write that
threw therefore left those reps marked durable while absent, and nothing ever retried them —
silently losing exactly the rep this write path exists to keep. The loop now advances one rep at a
time and only past reps that actually reached disk, so a failure is retried on the next tick; the
`(sessionId, repIndex)` upsert makes that retry free.

The logic moved out of the composable into `SessionRepository.persistPending`, because the ordering
*is* the durability guarantee and it was the one part of the write path that could not be checked by
reading it. It is now four tests in `SessionDurabilityTest`, using a DAO that delegates to real
SQLite with a fault injected at one rep index — a pure fake would let the test pass while the schema
rejected the row.

**`ON DELETE CASCADE` had never actually been exercised.** The original test used Room's
`clearAllTables()`, which is a bulk wipe that never touches SQLite's foreign-key machinery. There is
now a test that issues a real `DELETE FROM sessions WHERE id = ?` and asserts the reps and feature
samples go with it — the first proof that the `PRAGMA foreign_keys=ON` callback takes effect at all.

## Outstanding

- **The device gate is unrun.** "Entire patient session works in airplane mode" needs a phone, a
  performer and a flight-mode toggle. Nothing here has touched a real device.
- **Fault and cue events are not written yet.** The tables exist and the DAO is there, but §6.14's
  detector does not currently surface an event stream the UI can persist. Wiring that is small and
  belongs with 8.1, when faults actually have definitions to fire.
- **No recovery UI.** `unfinishedSessions()` answers the question and nothing asks it. A patient
  whose app was killed mid-set is not yet offered the session back — the data survives, the
  affordance does not.
- **`fallbackToDestructiveMigration`.** Correct while the schema moves pre-release, and a bug the
  moment a build is on someone else's phone. Becomes a real migration before any device but ours.
- **Exercise version is hardcoded to 1** (`BundleAssembly.kt`). Re-authoring the same catalogue
  exercise overwrites version 1's row and its `.rpose` file rather than creating version 2, which
  contradicts the §9.6 immutability the `(id, version)` key was chosen for. Dormant today — nothing
  reads back an older version — and it belongs with 7.4's assignment binding, where version binding
  first becomes load-bearing. Recorded here so it is not mistaken for working.
