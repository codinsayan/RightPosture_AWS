Status: in-progress

Scope: plan-defined feature set only.

Tests: synthetic stationary poses per feature; positive-z physical meaning.

Device gate: visually check angles while standing and moving.

User action: confirm cue direction empirically for every demo-used feature. Never guess Appendix A signs.

## Result

Code and JVM tests are complete. **The iteration is deliberately not marked `complete`** — its
device gate and its Appendix A user action cannot run yet. See "Outstanding" below.

- Added `core/pose/FeatureExtraction.kt`: all 15 features from the §6.5.3 table, `FeatureContext`,
  `Side`, and the `FeatureSigns` table Appendix A requires.
- Added `angleBetweenDegrees` to `Angles.kt`; `jointAngleDegrees` now delegates to it. Feature 7
  compares two free vectors rather than three points.
- Invalid features are **absent from the returned map** rather than present with a null. A missing
  ankle drops `ankle_dorsiflex_active` and nothing else; tests assert that isolation both for a
  non-finite landmark and for a zero-length limb.
- `activeSide` is an input, not derived. §6.2 resolves it per rep over the first 25% of the rep,
  which needs segmentation that does not exist until 3.4.
- Vertical reference follows §6.5.4 option (b): a nullable `verticalWorld`. Null means non-upright
  exercise or failed calibration, and the gravity-referenced features abstain.

### Plan discrepancy: feature 8 cannot be body-intrinsic

§6.5.4 states that for non-upright exercises only feature 7 (`trunk_flexion`) must be disabled,
and that features 8 (`trunk_lateral`) and 10 (`pelvic_obliquity`) "are computed entirely within the
body frame and remain valid in any body position."

Feature 10 is fine. §6.4 builds `x̂` by removing the longitudinal component from the hip line; the
raw hip line keeps that component, and it is exactly the hip drop being measured. Genuinely
body-intrinsic.

Feature 8 cannot be. §6.4 defines `ŷ` **as** the torso axis, so in body coordinates the torso axis
is identically `(0, 1, 0)`. A trunk lean measured against the body frame is therefore identically
zero for every pose — not noisy, not approximate, but structurally always 0. To produce any real
number, `trunk_lateral` needs an external reference.

Implemented against the vertical reference alongside feature 7, so it abstains when there is no
vertical. This contradicts §6.5.4's grouping and needs an owner decision before non-upright
exercises ship. It affects none of the four demo exercises.

### Outstanding — blocks `complete`

1. **Appendix A signs are placeholders.** Every entry in `FeatureSigns` is `+1`. Appendix A says
   "Verify each empirically. Do not infer them from the formulas," and §6.5.3 repeats it. Guessing
   here ships an arrow that confidently points the wrong way, so nothing was guessed and nothing was
   verified — the values are marked as unverified in source.
2. **The device gate cannot run yet.** It needs live camera and pose output, which arrive in 2.1 and
   2.2. Sequencing note: the iteration plan lists this gate at 1.5, but nothing capable of
   satisfying it exists until 2.2.
3. **Feature 15 interpretation.** §6.5.3 says "the shoulder-line normal and the hip-line normal";
   a line has infinitely many normals. Implemented as `line × ŷ`, the forward normal of each girdle.
   §6.5.3 already flags feature 15 as a coarse proxy and says to drop it with its mask rule rather
   than debug it during the event.
