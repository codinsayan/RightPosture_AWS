# Version 7.3 — Supabase authentication

Status: planned
Source: §4.1, §13, §19

**Deviation from the plan.** §4.1 names Firebase Auth/Firestore/Storage. Decided 2026-09-05 to use
Supabase instead — Auth, Postgres, Storage, one vendor. The reason is `demo.mp4`: §9 makes it part of
the `.rpose` bundle, a real demo recording measures roughly 4–22 MB (15–60 s at 30 fps, §Params
`VALIDATOR_MIN_DURATION_SECONDS`/`AUTHORING_ACCEPTANCE_TIMEOUT_SECONDS`), and that no longer fits in
a Firestore document field. Once object storage is required regardless of vendor, Firebase Storage's
requirement of a card on the Blaze plan and Supabase's card-free 1 GB free-tier storage stopped being
a wash. Verified 2026-09-05: Supabase's free plan needs no card ([pricing](https://supabase.com/pricing)),
and the Kotlin client is community-maintained, not first-party — actively updated as of mid-2026
([supabase-kt](https://github.com/supabase-community/supabase-kt)), but worth re-checking before
depending on it further into the project. Every place below that named a Firebase concept has been
translated to its Supabase equivalent; nothing else about §13's design (offline-first, Room as source
of truth, last-write-wins) changed.

**Known operational cost of this choice:** a Supabase free project pauses after 7 days with no
database activity. Data is not lost — it is frozen until restored from the dashboard, recoverable for
up to a year — but a demo rehearsed today and presented in three weeks needs either one query run in
the interim or the project restored the morning of. See v7.5's Outstanding section.

Scope: email/password sign-in and role record.

Tests: repository fakes; Supabase local dev stack (`supabase start`) if configured.

Device gate: two test roles sign in.

## Setup this needs from you

1. [supabase.com](https://supabase.com/dashboard) → **New project** → name it, choose a region, set a
   database password (save it — it is not shown again). No card.
2. **Project Settings → API** → copy the **Project URL** and the **anon public** key. These are the
   only two values the app needs; unlike `google-services.json` there is no file to place, they are
   two strings.
3. **Authentication → Providers → Email** → confirm it is enabled (on by default). Turn off "Confirm
   email" for the hackathon build — a confirmation email round-trip is friction a two-role demo does
   not need; turn it back on before anything resembling real use.
4. **Authentication → Users → Add user** → create one physio and one patient test account,
   Auto-confirm on, so I do not have to build a sign-up flow to test sign-in.
5. Run the SQL in v7.4's schema section (via **SQL Editor**) once both this and 7.4 are ready — it
   creates the `role` claim this iteration reads.

## Where the two strings go

Not committed as plaintext: `local.properties` (already gitignored by the Android Gradle template),
read into `BuildConfig` fields. The anon key is safe to ship inside an APK — it is designed to be
public and is constrained by Row Level Security, not secrecy — but keeping it out of source control
means a leaked repo does not also leak whichever project it points at.

## Result — 2026-09-05

### The SDK was abandoned, and why

`supabase-kt` 3.8.0 forces `kotlin-stdlib` to **2.4.0**. This project's KSP is 2.0.21-1.0.28 (needed
by Room), and it cannot read 2.4.0 metadata — the build fails with
`[ksp] [MissingType]: Element 'RightPostureDatabase' references a type that is not present`, before
any of our own code compiles. Bisected by removing dependencies one at a time: without Supabase the
toolchain settles on the **2.3.21** stdlib AGP 9's built-in Kotlin supplies, and everything builds.

Rather than upgrade the Kotlin toolchain underneath a green 553-test suite to satisfy one library,
`sync/SupabaseClient.kt` talks to the same HTTP API the SDK wraps. Supabase *is* PostgREST and
GoTrue over HTTP, and the surface this project needs is small. Three things fall out of that:

- the dependency risk flagged when the backend was chosen — `supabase-kt` is community-maintained,
  not first-party — disappears;
- every call is mockable with Ktor's `MockEngine`, so the whole auth path is tested in the JVM suite
  with **no network and no project**;
- the toolchain stays where it is.

### Not configured is a supported state, not a broken one

`SupabaseConfig.isConfigured` is checked at every call site. With no URL and key in
`local.properties` the app uses `LocalOnlyAuthRepository`, skips sign-in entirely and behaves exactly
as it did before this iteration. §13.3 and 7.1's airplane-mode gate both depend on that being true,
and "continue without an account" keeps it true even on a configured build — being unable to sign in
must never be what stops someone exercising.

Half-configured is treated as unconfigured. Pasting the URL and forgetting the key is the likelier
mistake, and it must not look ready or every call fails at the server instead of being skipped.

### Two decisions worth stating

- **Role is a table row, not a JWT claim.** A custom claim needs an Edge Function on signup to write
  it into the token — more moving parts than a two-role demo justifies. The cost is one extra request
  after sign-in, off the critical path.
- **A missing role row defaults to patient.** Failing to the *less* privileged role on purpose: a
  physio wrongly shown the patient flow is inconvenienced, whereas a patient wrongly shown authoring
  can overwrite the reference their own exercises are scored against.

`AuthOutcome` separates `Rejected` from `Offline` deliberately. Telling a patient their password is
wrong when the wifi is down sends them to reset a password that was fine.

### Schema

`supabase/schema.sql` — §13.2's mirror redrawn relational, plus row-level security on **every**
table. That is not optional: PostgREST exposes these with the anon key, and the anon key ships inside
the APK, so a table with RLS off is readable by anyone who has the app. The Storage bucket is private
for the same reason — a `demo.mp4` is a recording of a real person.

### Tests

`SupabaseAuthTest`, 9 cases against `MockEngine`: unconfigured builds; half-configured builds;
successful sign-in reading the role row; a missing role row defaulting to patient; a wrong password
carrying the server's own wording; an unreachable server reported as offline rather than rejection;
sign-up writing the role; sign-up with email confirmation on saying what to actually do; a duplicate
account; and an HTML error page still producing an actionable message.

`./gradlew testDebugUnitTest` — 563 tests, all pass. `assembleDebug` builds.

### Outstanding

- **No project exists yet.** Every branch is tested against a mock; nothing has touched a real
  Supabase instance. Needs the setup steps above, the two values in `local.properties`, and
  `schema.sql` run once.
- **The session is not persisted across launches.** The access token lives in memory, so a restart
  returns to sign-in. Refresh-token storage belongs with 7.5, when a background sync needs to
  authenticate without a user present.
- **Nothing syncs yet.** 7.3 is identity only; 7.4 and 7.5 are the data paths.
