# Version 2.1 — Camera preview

Status: complete  
Source: §12.1, §5.2

Scope: CameraX preview, permission, front default, latest-frame backpressure, 720p analysis.

Tests: permission state logic.

Device gate: preview rotation and lifecycle pass. User grants camera permission.

## Result

- Added `camera/CameraController.kt` (CameraX binding), `camera/CameraPermission.kt` (pure
  permission state logic), and `camera/CameraPreviewScreen.kt` (Compose UI). `MainActivity` now
  routes to the preview instead of the v0.3 axis diagnostic, which stays in the repo unrouted so
  the v0.3 measurements remain reproducible.
- Front camera is the default, per §6.2's recommendation. `CameraFacing` is reused from
  `core.pose` rather than redeclared.
- `STRATEGY_KEEP_ONLY_LATEST` and `OUTPUT_IMAGE_FORMAT_RGBA_8888` as §12.1 specifies.
- Permission logic is a pure function of three booleans, so it unit tests without Robolectric or an
  instrumented run. It distinguishes "never asked" from "permanently denied" — Android reports no
  rationale for both, and only the app knows whether it has already asked. Without that split the
  UI offers an Allow button that silently does nothing.

### Three defects found and fixed by the device gate

1. **Rotation was broken.** In landscape the preview rendered sideways. `setTargetRotation` was
   being fed `view.display?.rotation`, but at bind time the `PreviewView` is not attached, so its
   display is null and every orientation bound as `ROTATION_0`. Rotation is now read from the
   Activity's display in the composable and passed into `bind`, which also rebinds when it changes.
   `Preview` no longer sets a target rotation at all — `PreviewView` applies the display transform
   itself and setting both fights it. `ImageAnalysis` does still need it, since it has no view to
   correct it, and that is what will keep 2.2's landmark coordinates orientation-consistent.
2. **The analysis stream was 1920×1440, not 720p.** §12.1's snippet asks for `Size(720, 1280)`.
   That bound is portrait-oriented; the camera advertises landscape sizes, so it matched nothing and
   `FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER` resolved *upwards*. Corrected to a sensor-oriented
   `Size(1280, 720)`, a 16:9 aspect strategy, and `CLOSEST_LOWER_THEN_HIGHER` so the fallback
   undershoots rather than overshoots. Measured 1920×1440 at 15 fps before, 1280×720 at 24 fps
   after.
3. **The fps counter raced.** It mutated Compose state from the analysis thread and forced a
   recomposition per frame. Replaced with an `AtomicInteger` sampled once a second from a
   `LaunchedEffect`.

Points 1 and 2 are both cases where the plan's own code snippet does not do what the plan's prose
asks for on this CameraX version. Neither is visible from a unit test.

need the GPU or NPU delegate rather than CPU.
