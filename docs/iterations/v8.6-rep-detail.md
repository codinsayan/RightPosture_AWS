# Version 8.6 — Rep-by-rep detail and not-counted reasons

Status: complete  
Source: §14.1, §14.2, §6.6, §6.12.4

Scope: readable per-rep rows that separate how well a rep scored from why it was not counted, plus
numeral highlighting in the generated summary.

Tests: a rep that scored well and still did not count says both things; no rejection phrase trips the
summary validator's word lists; an unscored rep is never rendered as zero.

Gate: the report states quality and countability as the two independent facts they are, and never
prints a raw enum name.

---

## Why

The session report renders this:

    Rep 1: 94 · SKIPPED

It reads like a bug. It is not.

`ExerciseEngine.closeRep` (`ExerciseEngine.kt:395-420`) computes quality from the rep's scored frames
**before and independently of** the validity decision:

    val quality = repScore(frames = repFrames.toList(), ...)
    val valid = completed.valid && quality != null

So `valid` is the AND of two separate judgements — the PhaseTracker's §6.12.4 structural verdict, and
the scorer's. A rep can match the reference on every frame the scorer saw (quality 94) and still be
refused because it jumped to the end position without the movement in between (`SKIPPED`). Both facts
are true. The report just states them as one cryptic line, in a vocabulary only the code uses.

The invariant is precise and worth writing down, because any query over this data can get it wrong:

- `rejection != null` ⟺ `valid == false`
- `quality != null` is **orthogonal** to `valid`

Never treat `quality != null` as a proxy for "counted". Filter on `valid`.

## Shape

**`report/RepReadout.kt`** (new, pure) — `RepReadout(repIndex, headline, quality: Int?, counted,
detail)` and `repReadoutsOf(reps)`. Four branches, because the two facts are independent:

| quality | valid | headline |
|---|---|---|
| 94 | false | `Rep 3 · scored 94 · not counted` + a detail explaining both |
| null | false | `Rep 3 · not scored · not counted` |
| 94 | true | `Rep 3 · 94` |
| null | true | `Rep 3 · counted, not scored` |

The last row is unreachable today, since `valid = completed.valid && quality != null`. Render it
honestly anyway rather than crashing if that invariant ever moves.

`rejectionReason(raw)` resolves via `RepRejection.entries.firstOrNull { it.name == raw }` and falls
back to the raw string lowercased. It must not use `valueOf`: `SessionFactsTest.kt:54` stores the
string `"too fast"`, which is not an enum name, and `valueOf` would throw on real stored data.

Report tense — past, third person. Deliberately **not** reusing `EnglishPhrases.rejection`, which is
imperative live coaching ("go all the way down") spoken during the set, not read afterwards.

| Rejection | Report phrasing |
|---|---|
| `RANGE` | it didn't reach the full range |
| `TOO_FAST` | it was faster than the movement allows |
| `TOO_SLOW` | it was slower than the movement allows |
| `UNSEEN` | the camera lost sight of you |
| `UNSCORED` | no frame in it could be scored |
| `SKIPPED` | it jumped to the end instead of following the whole movement |

### The trap

**`SKIPPED`'s phrasing must not contain the substring "skip".** Verified at `SummaryValidator.kt:46`:
`"skip"` is in `UNSAFE_ADVICE_WORDS`. These phrasings reach the prompt through `topRejection` (8.7),
the model echoes them back, and the validator would then reject its own input — twice, silently, with
every summary falling to the template and nothing on screen saying why.

Same reason `"stop doing"`, `"give up"`, `"consult"` and `"heavier"` are avoided. The checks are
substring matches on lowercased text, so they are aggressive by construction: `"strain"` hits
"restrain", `"condition"` hits "conditioning". A test iterating `RepRejection.entries` through
`checkSummary` proves the wording stays clean when someone adds a seventh enum value.

## Numeral highlighting

Promote `NUMBER_RUN` (`SummaryValidator.kt:50`) from `private val` to `internal val`, and add
`core/summary/Numerals.kt` with `numeralRanges(text)` using that same regex. The Compose wrapper uses
`buildAnnotatedString` + `withStyle(SpanStyle(fontWeight = SemiBold, color = TRACE))`.

Sharing the regex is the load-bearing part. Rule 1 of `checkSummary` already rejects any digit run not
in `facts.allowedNumbers()`, so in an accepted summary **every numeral is a measurement we computed** —
highlighting is safe by construction. A second, hand-written regex could highlight something the
validator never checked, which is exactly the claim the highlight makes to the reader.

Weight and colour, not a background box: the summary is `bodyLarge` prose in a Column with no Surface,
and a highlight box would read as a rendering bug. `SpanStyle` does not affect TalkBack.

## Tests

`RepReadoutTest.kt`:

- a rep that scored well and still did not count says both things — quality 94 with `SKIPPED`: `"94"`
  appears, `counted == false`, and the detail contains neither `"0"` nor the raw token `"SKIPPED"`
- an unscored rep is never rendered as zero
- every `RepRejection.entries` value has non-blank wording, with no underscore, and `!= entry.name`
- no rejection phrase trips the validator's word lists — each run through `checkSummary`
- an unrecognised rejection string degrades to something readable (the stored `"too fast"` case)

`SummarySafetyTest.kt`: every numeral in an accepted summary is one `allowedNumbers()` permits — the
test that makes the highlight honest.

## Result

Built as planned. 701 tests, up from 691.

`report/RepReadout.kt` holds the four branches; `SessionReportScreen` moved out of `AppHost.kt` into
its own file, which took the host from 852 lines to 673. The rep list is now a headline plus an
explanatory line, under an "Every rep" heading.

### The wording constraint was real

`no rejection phrase trips the summary validator` runs every `RepRejection` value through
`checkSummary`, and it earns its place: `"skip"` is in `UNSAFE_ADVICE_WORDS`, so describing `SKIPPED`
with the obvious word would have rejected every summary that mentioned it. The failure mode is the
nasty kind - two rejections, a silent fall back to the template, and the only visible symptom a line
reading "Summary from measurements only". The phrasing that shipped is "it jumped to the end instead
of following the whole movement".

`rejectionReason` resolves by name rather than `valueOf`, because stored rows are not guaranteed to
hold enum names - `SessionFactsTest` writes the string `"too fast"` - and `valueOf` would throw on
real data rather than on a fixture.

### Highlighting

`NUMBER_RUN` went from `private` to `internal` and `numeralRanges` shares it, so the numbers the
screen emphasises are exactly the ones the validator checked. That sharing is the safety argument:
rule 1 refuses any digit run outside `allowedNumbers`, so in an accepted summary every numeral is a
measurement we computed. A second regex here would eventually disagree, and the first symptom would
be a highlighted number nobody validated.

A test pins `1.8` as one numeral rather than two, which is also why 8.7 keeps every emitted fact
integral.

### Outstanding

`Rep · counted, not scored` is unreachable while `valid = completed.valid && quality != null` holds.
It is rendered rather than treated as impossible, so a future change to that invariant produces an
honest line instead of a crash.
