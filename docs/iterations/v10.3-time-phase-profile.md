# Version 10.3 — Time to phase profile

Status: in-progress — implemented and unit tested; device gate not yet run.  
Source: §6.8.1; new work, required by lead mode specifically

Scope: for the median rep, phase sampled at 101 evenly spaced points through the rep's **duration**,
plus the median rep duration in seconds. Stored alongside 10.2's poses.

This is the one place in the reference pipeline that indexes by time rather than by phase, and it
exists only because the ghost leads.

Phase is derived from the dominant joint's **value** and deliberately carries no timing — §6.8.1 is
emphatic about this, and it is what makes scoring fair to a patient working at their own speed. It
also makes phase useless for driving a demonstration. An end-range hold occupies one phase bin and
several seconds, so a ghost advanced linearly through phase over `periodSeconds` would skip straight
through the part of the exercise the physio spent longest on — which for most therapeutic exercises
is the part that matters.

`phaseProfile()` already produces per-frame phase for each rep, and frames arrive at a fixed rate,
so frame index is time. Normalise each rep's time axis to [0,1], resample, take the median across
reps.

Tests: the profile is non-decreasing; it spans the movement; replaying it at the stored duration
reproduces a deliberate end-range pause rather than sliding through it.

Device gate: record an exercise with a deliberate two-second pause at end range. The profile must
flatten there. A profile that climbs smoothly through the pause means the time axis is not being
measured, and the ghost will lead the patient through a movement the physio never performed.

## Result

- `core/reference/SkeletonReference.kt` — new `PhaseTiming(phaseByTime, repDurationSeconds)` with
  `phaseAt(elapsedSeconds)` (clamps both ends; past the end holds the last sample) and an `init`
  that refuses a profile going backwards or a non-positive duration — the load-time validation the
  first trap asks for, so 10.4 gets it for free when it constructs one from JSON.
  `SkeletonReference` gains `timing: PhaseTiming`, built inside `buildSkeletonReference` from the
  **same reps** as the poses, so the ghost has one median rep rather than poses from one set of reps
  timed by another. New `resampleOverTime` (internal). Each rep is normalised onto its own [0, 1]
  before the pointwise median, per the second trap.
- `diagnostic()` now also logs `rep=<seconds>` and `endHold=<share>` — the share of the rep spent
  within 3 phase of the turnaround. That is the device gate in one number.
- `PhaseTimingTest` — 9 cases: non-decreasing and spanning 0→100; duration equals the generator's
  3 s rep; a 2 s end-range pause replays as ≥ 1.5 s held at the turnaround; a 2 s pause flattens the
  profile far more than a 0.5 s beat; timing and poses share reps; held past the end, clamped
  before the start; interpolated in time; backwards profile refused; zero duration refused.

Commands: `gradlew testDebugUnitTest assembleDebug` — BUILD SUCCESSFUL; 816 tests, 0 failures.

Device gate: **not yet run.** Record an exercise with a deliberate two-second pause at end range,
then once more without one. The `RPGhost` line's `endHold` must be clearly larger for the paused
recording. Similar values mean the time axis is not being measured.

## Traps

- Phase is non-decreasing by construction upstream (§6.8.3), so a profile that is not says the
  builder is wrong, not that the physio moved oddly. Validate it on load (10.4) as well as here.
- The median across reps of a monotonic family is monotonic — but only if each rep's axis is
  normalised *before* the median, not after.
- Past the end of the rep, hold the last sample rather than wrapping. The cycle boundary belongs to
  the clock (10.8), which is the only part that knows about the rest beat between reps.
